# Backend Rewrite Constitution

## Core Principles

### I. Resource Budget as a Design Constraint

Every design decision is evaluated against a fixed, measured budget before it is accepted.
The development target is an Intel Core i3-1005G1 (2 cores, 1.20 GHz) with 8 GB of RAM.

- The production API binary MUST NOT exceed 150 MB resident memory at idle.
- A local development stack (database, cache, API) MUST fit within 2 GB of RAM.
- Any proposal that pushes the local stack above 3 GB MUST be rejected unless it
  carries an explicit, written justification naming what breaks without it.
- Container count is a design output, not an input. Adding a service that cannot be
  justified by a measured need violates this principle.
- Performance budgets MUST be stated as numbers in specifications and verified by
  benchmark or measurement, not estimated.

Rationale: the previous 14-container architecture caused a blue screen of death on the
target hardware. Resource exhaustion is the primary failure mode this project must avoid.

### II. One Process Before Many

A new process boundary requires evidence that a single process cannot satisfy the
requirement. Splitting is the default outcome of convenience, not of design.

- The system MUST run as one API process plus infrastructure dependencies.
- A service MUST NOT be created for a capability that can live in the API process.
- Inter-service calls MUST NOT exist without a documented boundary justification
  (independent scaling, isolation of failure domains, or separate release cadence).
- Shared business logic MUST live in one place. Duplicating logic across services is
  a defect.
- Retiring a service is a valid and preferred outcome when it has no callers.

Rationale: the previous four microservices had zero inter-service communication and no
callers from the main API. They were dead code carrying a full deployment cost.

### III. Persistence Is Not Optional

Any state the system accepts from a client and reports back MUST survive a full process
restart.

- In-memory `Map`, slice, or struct storage for business data is FORBIDDEN. The only
  permitted in-memory state is derived cache that can be rebuilt from the database.
- Financial or payment outcomes MUST NOT be produced by a random or simulated function
  in production code paths. Test doubles MUST be unreachable from production binaries.
- Identifiers MUST be generated by the database or a collision-resistant scheme.
  Timestamp-plus-random concatenation is NOT sufficient.
- Every schema change MUST be a versioned migration. Exactly one schema definition is
  authoritative per deployment target.

Rationale: five stores across the previous codebase were lost on every restart, and
payment success was decided by `Math.random()`.

### IV. Test-First and No Unbacked Claims

Behavior is demonstrated by an executable test. Documentation describes only what
exists and has been verified.

- Test-Driven Development is mandatory for business logic: write the test, watch it
  fail, then implement.
- Every endpoint in the API MUST have at least one test that exercises it end to end.
- `go test ./...` MUST pass before any commit to the default branch.
- Documentation MUST NOT describe endpoints, features, commands, or infrastructure
  that are absent from the repository. If it is not committed and tested, it does not
  exist.
- Test coverage below 70% on changed packages MUST block merge.

Rationale: the previous repository carried 47 documents for 196 source files, promising
endpoints, scripts, and directories that were never implemented.

### V. Observability Built In, Not Bolted On

Operational capability is part of the feature, not a follow-up task.

- Structured JSON logging to stdout is MANDATORY. Every log line MUST carry a
  correlation ID propagated from the inbound request.
- All HTTP handlers MUST emit Prometheus metrics: request rate, error rate, and latency
  percentiles (p50, p95, p99) per route.
- OpenTelemetry traces MUST be emitted for outbound calls to external services.
- Every endpoint MUST expose a health check that reports real dependency status,
  including database and cache reachability.
- A feature that cannot be diagnosed in production MUST NOT ship.

Rationale: the observability assets in the previous repository (Grafana, Prometheus,
Loki, Jaeger, Sentry) were never wired to anything and cost maintenance with no return.

## Technology Constraints

- **Language**: the API is written in Go. Static binary, standard library logging.
- **Database**: PostgreSQL 16 is the only supported datastore. SQLite is prohibited;
  it cannot represent the concurrency the system requires.
- **Query layer**: typed query generation (`sqlc` or `ent`). No runtime ORM abstraction
  and no string-concatenated SQL.
- **Authentication**: JWT with a maintained library. Password hashing MUST use bcrypt or
  argon2 with a current cost factor.
- **Cache and queues**: if a job queue is introduced, Redis MUST run with
  `maxmemory-policy noeviction`. Any other eviction policy silently destroys queue keys
  without raising an error and is prohibited.
- **Observability**: Prometheus for metrics, OpenTelemetry for traces, Loki for logs.
- **Containers**: container images MUST build from a single-stage, multi-stage-clean
  definition, and MUST be verified to build in CI before merge.
- **Deprecated dependencies are prohibited**: libraries with an archived repository or a
  published deprecation notice MUST NOT be added.

## Security Requirements

- Secrets MUST NOT be committed to the repository in any form, including configuration
  files and example files. Use environment variable substitution with documented names.
- Authentication and authorization are enforced on every non-public route. A missing
  middleware registration is a release blocker.
- All user input MUST be validated at the boundary before reaching business logic.
- Security headers and request size limits MUST be applied by default.
- Third-party webhook and callback endpoints MUST verify signatures before acting.
- Any credential that has been exposed in a committed file MUST be treated as
  compromised and rotated; removing it from history is not sufficient.

## Development Workflow and Quality Gates

The Spec Kit SDD flow governs all work: **constitution, specify, plan, tasks, implement,
converge**. Implementation MUST NOT begin without an approved specification.

1. Every feature starts with `/speckit.specify`, producing a specification with
   acceptance criteria and a resource budget drawn from Principle I.
2. `/speckit.plan` produces the technical plan and MUST record the process count the
   design implies.
3. `/speckit.tasks` breaks the plan into independently verifiable units.
4. `/speckit.implement` executes tasks with a failing test preceding each behavior.
5. `/speckit.converge` verifies the implementation against the specification and the
   principles in this document.

Quality gates, all mandatory:

- `go build ./...` succeeds.
- `go test ./...` passes.
- `go vet ./...` reports no findings.
- Container image builds successfully.
- No committed secret, verified by automated scan.
- No new process boundary introduced without a written justification.

`/speckit.analyze` MUST be run before implementation when a specification covers more
than one feature or crosses architectural boundaries.

## Governance

This constitution is the authoritative source of engineering rules for this project. It
supersedes the 47 documents in `docs/`, which describe a superseded architecture. Those
documents MUST NOT be treated as requirements until individually re-validated against
the current specification and marked as current.

**Amendment procedure**:

1. Propose the change with written rationale identifying which principle is affected.
2. Amend this file, recording the version bump and the Sync Impact Report content.
3. Any change that relaxes a core principle requires an explicit justification in the
   pull request description and is reviewed by the maintainer.
4. Update the specifications that depend on the amended principle.

**Versioning policy** (semantic versioning of the constitution itself):

- **MAJOR**: removing a principle, or redefining one in a backward-incompatible way.
- **MINOR**: adding a principle or section, or materially expanding existing guidance.
- **PATCH**: clarifications, wording fixes, or non-semantic refinements.

**Compliance review**:

- Every pull request MUST state how it complies with, or why it need not address, each
  core principle. "Not applicable" requires a reason.
- Compliance is verified by the gates listed above, not by assertion.
- A deliberate, documented violation is permitted; an undocumented one is a defect.
